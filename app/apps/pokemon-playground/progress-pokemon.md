# Pokémon Playground — Progress & Planning

Read this file first when resuming work on this app. Companion to the root
`docs/PROGRESS.md` (tracks the whole portfolio site) — this one tracks just
this app's build.

Demo app for jdlarrea.com portfolio. Small square canvas/DOM area where a character walks around a scene, can enter a house to sleep, walk through grass or fish at a lake for random Pokémon encounters using PokeAPI data.

## Stack decisions

- **Framework: Next.js, not Vite.** This app was originally scoped as a standalone Vite + React project in an earlier planning chat, before this portfolio's `/apps` routing was designed. That's since been superseded — **corrected 2026-09-04**: it lives at `app/apps/pokemon-playground/page.tsx` (`"use client"`) inside the main portfolio's Next.js app, deployed together on Vercel, not as a separate project. Colocated components/helpers go in `app/apps/pokemon-playground/_components/` and `_lib/` (underscore prefix opts a folder out of Next's App Router route-scanning — see root `docs/PROGRESS.md`'s app-components discussion for why).
- **Shell:** `app/apps/layout.tsx` already provides the logo + floating "back to main site" button for every app under `/apps/*` — this page doesn't need to build any of that itself.
- **Theme: light, not this site's dark theme.** The main portfolio is always-dark via a `dark` class scoped to `(main-site)`; `/apps` deliberately omits it, so shadcn's default *light* tokens apply. Build this app's UI with the generic shadcn semantic classes (`bg-background`, `text-foreground`, `border-border`, `bg-card`, etc.) or plain Tailwind — **not** this site's dark-hardcoded custom tokens (`bg-dark-*`, `body-*`, `accent-*`, `bdr-*`), which aren't theme-reactive and will look wrong on a light background.
- **Rendering:** DOM, not `<canvas>`. Area tiles/sprites are absolutely-positioned `<Image>`s/`<div>`s with `top`/`left`/`width` in **percentages** of the container (not px) so the layout scales cleanly. (Original plan said `transform: translate()`; the build uses `top`/`left`. Switching the *character* to `transform` is a known optional perf improvement — skips layout recalculation — not needed at this scale.)
- **Container:** `aspect-square`, `max-width` constrained, resizes responsively, stays square at all viewport widths.
- **Data source:** PokeAPI (no auth/key needed for basic sprite + species data).
- **State management:** Plain React state/refs for now — no external state library needed at this scale.
- **Persistence — decided 2026-09-08: Neon Postgres, not `localStorage`.** Superseded — the original `localStorage` idea was from before the demo-login/multi-user plan existed; caught Pokémon need to persist per dummy user account, across devices/sessions, which `localStorage` can't do. See "Database plan" below for the schema.
- **PokeAPI usage — no live calls during gameplay, decided 2026-09-08.** A one-time seed script pre-fetches and stores a small, curated subset of fields (id, name, sprite URL, etc.) for only the specific Pokémon IDs used in the grass/water pools — into this app's own DB, not fetched live. Encounters read purely from that local catalog; PokeAPI is only ever hit once, at seed time, never during actual play. Chosen for demo reliability (no loading spinner mid-encounter, no dependency on PokeAPI's uptime while someone's actually testing the live site) — this is a portfolio demo, not a use case that needs live data freshness. See "Database plan" below.
- **IP/attribution note:** storing a few cached fields from PokeAPI isn't a meaningfully different legal act than fetching them live — same public data either way. Practical risk for a small non-commercial portfolio demo is low (PokeAPI is built for exactly this kind of fan use, and there's a long precedent of similar hobby/portfolio projects). Still worth a small on-page disclaimer for polish: *"Pokémon and Pokémon character names are trademarks of Nintendo/Game Freak/The Pokémon Company; this is an unofficial fan-made demo, not affiliated with or endorsed by them."* Not legal advice — just the practical read.
- **Scaling system (added 2026-09-08):** the whole scene is designed against a fixed **640px reference canvas** (`SIZE_CANVAS` in `_lib/utils.ts`) — chosen as a clean multiple of 16px (40 tiles), matching the pixel-art assets' native tile size. `.canvas-main` is `max-w-160` (640px). Every sprite/zone's `%` size is derived from its **native pixel size ÷ 640** via the `spriteSize(px)` helper (`_lib/utils.ts`), not hand-picked round percentages — this is what keeps a sprite's visual footprint and its (future) collision hitbox scaling together consistently at any screen width, instead of drifting apart. Decorative-only sprites (no hitbox) are free to ignore this and use whatever px size looks good. See `docs/PROGRESS.md` for the fuller reasoning trail (percentage-vs-fixed-grid discussion) if this needs re-deriving later.

## Core mechanics (from planning discussion)

- **Movement — implemented 2026-09-08:** Keyboard (`keydown`/`keyup`) + on-screen D-pad buttons (`onPointerDown`/`onPointerUp`/`onPointerLeave`/`onPointerCancel`, covering both mouse and touch via the Pointer Events API) both call the same shared `startMoving`/`stopMoving` functions, which add/remove from one `Set<Direction>` (held in a `useRef`, not state — membership changes shouldn't themselves cause a re-render). A `requestAnimationFrame` game loop (`tick()`, self-rescheduling every frame) reads that Set each frame and resolves it down to **exactly one** active direction — the most recently pressed one that's still held, taken via `[...activeDirections.current].at(-1)` (Sets iterate in insertion order) — rather than summing every held direction's delta. **This was a deliberate decision, not an oversight:** summing deltas allowed diagonal movement, which doesn't fit this game's 4-direction sprite/facing model. Resolving to a single direction this way also naturally falls back to a second still-held direction when the primary one is released, with no extra bookkeeping. `MOVE_SPEED` (currently `0.1`, in `character.tsx`) is the per-frame `%` step — tune by feel, not by formula.
- **Canvas edges — implemented 2026-09-27:** not a `Zone`, just a clamp on the character's *proposed* position each frame — no AABB check needed, since there's no "object" at the world's edge. Range is `[0, 100 − CHARACTER_SIZE]`, not `[0, 100]`, because position is the sprite's **top-left corner** (clamping to 100 would let the whole sprite sit off-canvas). Lives in `_lib/utils.ts` as pure helpers: `clamp(value, min, max)` and `clampToCanvas(position, size)` (takes `size` as a param rather than importing the character's, so it stays reusable). Position state was merged from separate `coordX`/`coordY` into one `position: Position` (`{ x, y }`) object with one `setPosition` updater — required so a single propose → check → commit updater sees both axes at once, which step 5's rectangle-overlap check needs. Always return a **new** object from the updater (never mutate `pos`), or React's `Object.is` check skips the re-render. No "!" bump reaction at canvas edges (that's for bumping an actual thing).
- **Area model — redesigned 2026-09-27 (supersedes the 2026-09-08 solid/trigger split below it).** Four encounter areas, two kinds:
  - **"Wander" areas — grass (`area-grass.tsx`) + dirt (`area-dirt.tsx`, added 2026-09-27):** walkable, never block movement. A few random tiles inside each are "live" triggers; overlapping one starts an encounter immediately (no prompt). See "Grass/dirt encounters" below.
  - **"Edge" areas — lake (`area-lake.tsx`) + tree cluster (`area-tree-cluster.tsx`):** **solid** (can't walk in). Pressing a direction *into* the edge while blocked surfaces a prompt — lake: "Want to go fishing?"; trees: "Want to watch for birds?" (working copy). Confirm → a fishing-pole / binoculars icon spins for 3s (visual only) → the encounter-or-not result is **pre-rolled** when the attempt starts, revealed after the 3s. No encounter → lake: "No bites this time!"; trees: "Couldn't detect any flight activity!". Encounter → the shared encounter dialog. Implementation note: "moving into the edge" = the solid check blocked the move **and** the held direction points at that zone — detection piggybacks on solid collision. Needs a release-and-re-press guard (like the old "!" design) so dismissing the prompt while still holding the key doesn't immediately re-prompt.
  - **Not encounter areas:** house (sleep/wake, below); shrubs (`terrain-objects.tsx`, decorative, walk-over, **no collision** — confirmed 2026-09-27); sunflowers (collision TBD).
  - **The "!" bump reaction** (below) no longer applies to the lake or trees — their bump becomes the prompt instead. Kept only for any future plain solid obstacle (e.g. sunflowers, if they become solid).
- **Zones — solid vs. trigger, clarified 2026-09-08 (partly superseded, see Area model above):** not every zone blocks movement. **Solid** (block movement, get the "!" bump reaction below): tree, lake's water body. **Trigger-only** (never block movement, just fire an event on overlap): house, the lake's walkable edge, grass tiles. Data-driven, each zone a rectangle (`x/y/width/height` in %, top-left-anchored — doesn't need to match how a zone's *visual* sprite happens to be anchored). Collision test = standard AABB (axis-aligned bounding box) overlap check — two rectangles overlap only if they overlap on both axes at once. Each area component (`area-lake.tsx`, `terrain-objects.tsx`, etc.) exports the zones it owns, same pattern as the house-door landmark export; the character's `tick()` imports and checks against them before committing a move. Helper naming agreed 2026-09-27: name by return value — `rectsOverlap(a, b)` (shared AABB primitive), `isBlocked(...)`, `getTriggeredZone(...)`.
- **"!" bump reaction (originally the Tree design — now only for plain solid obstacles, see Area model):** **Bump-reaction design, decided 2026-09-08 (not yet implemented):** on collision, show a "!" above the character's head for exactly 1s (purely visual, no dismissal needed), and require the player to fully release + re-press the direction to move again — the 1s timer only controls the "!" bubble, not when movement is allowed again. Running into the same blocker again just re-triggers the same reaction. Chosen deliberately over a timer-based stun: no `setTimeout`/countdown state needed for the block itself (just call `stopMoving(direction)` immediately on collision), and it mildly discourages repeatedly bumping into obstacles on purpose without fully preventing a player who wants to. Two implementation notes: (1) for **keyboard**, the browser's own key-repeat will keep firing `keydown` for a still-held key even without a real release — guard with `if (e.repeat) return;` in `handleKeyDown`, otherwise the direction silently re-enters the Set on the next repeat event. (2) For **buttons**, not an issue — `onPointerDown` only fires once per physical press. This same "movement forced off" mechanism is expected to double as how the house dialog and encounter dialog freeze the character later — build it generically, not as a tree-only special case.
- **House / Sleep-Wake:** Trigger-only zone (does not block movement). `gameState: "exploring" | "sleeping"` state machine.
  - Character walks into house zone → "Go to sleep?" prompt.
  - Confirm → dark overlay covers scene, character disappears, only "Wake up" control available. All movement/input disabled while sleeping.
  - Wake → overlay clears, character reappears just outside the house door, state returns to `"exploring"`.
- **Grass/dirt encounters** (dirt added 2026-09-27, same mechanic) **— redesigned 2026-09-08, replaces the original "roll a chance every step" idea.** That original design assumed discrete tile-stepped movement; this game has continuous movement instead, so there's no natural "step" to roll a probability on (this is what the old open question below was stuck on). New design: within the grass zone, 2–3 specific tiles are "live" at any time (picked from the zone's valid tile positions). Walking onto a live tile **guarantees** an encounter — no roll. The specific Pokémon for a live tile is decided **the moment the tile is randomized into "live" status**, not when the player steps on it (equivalent player experience either way — they never see the roll — but simpler to test/debug, since a tile's assigned species can be inspected before it's ever reached). After an encounter resolves, 2–3 new tiles are randomized live, with exclusion rules (not the same tile, at least N tiles away from the previous one). Decided against tile-hunting concerns being a real problem here, since the zone has enough tiles that this should read as natural wandering, not a puzzle — revisit if playtesting says otherwise. **Note (2026-09-27):** both grids now contain `null` cells (roughened edges / irregular shapes) — live tiles must only ever be picked from non-null cells.
- **Lake encounters ("fishing") — partly superseded 2026-09-27, see Area model (no "!"; prompt is triggered by pushing into the solid edge, not a separate edge zone; 3s spinning-icon reveal):** The lake's water body is a **solid** zone (can't walk into it, gets the "!" bump reaction like a tree) — the player can only ever reach its **edge**, a separate **trigger-only** zone. Standing on the edge surfaces an explicit "Go fishing?" prompt (not automatic-on-touch, unlike grass) — confirming rolls a probability (tunable, not guaranteed like grass) for whether an encounter actually happens. Same encounter dialog as grass, different (water-type) Pokémon pool.
- **Encounter dialog — redesigned 2026-09-27, shared by all 4 areas:** actions: **"Throw a Pokéball!"**, **"Feed a berry first"**, **"Run away"**. A catch number is **pre-rolled when the encounter starts** (e.g. 5/10). Feeding a berry adds **+1**. Throwing succeeds if the number meets the **catch threshold (6/10)**; otherwise the Pokémon flees. Rarity sets the base: common Pokémon base ~5 (so a berry reliably gets them to 6), legendaries/rares lower (can't reach 6 even with a berry, or rarely). **Open:** exact roll formula — how random and rarity base combine (see Open questions). Species is pre-assigned (grass/dirt: when the tile goes live; lake/trees: when the attempt is pre-rolled), pulled from this app's pre-seeded catalog, not a live PokeAPI call — see "Database plan" below.
- **Caught Pokémon storage:** Neon DB, per dummy user account (see "Database plan" below) — not `localStorage`, not an in-memory list. **Per-user cap** on caught Pokémon (keeps the public demo DB small/safe — same idea as the planned Food Tracker item/meal caps). Once full, further catches are blocked; a **"release"** action in the Pokédex frees up a slot. The not-yet-built controls pane (planned for below the game canvas) will need a "storage full, release some Pokémon to catch more" message for this state.
- **Future/stretch ideas (not in scope yet):** a "playground" area to let caught Pokémon interact/play, other limits/rules TBD.

## Database plan (decided 2026-09-08, not yet built)

Neon Postgres. Two tables, standard normalize-by-reference shape — avoids duplicating the same species data on every catch:

- **Species catalog** (`id`, `name`, `sprite_url`, maybe `base_experience`/`height`/`weight` for Pokédex flavor) — seeded **once** via a small script that hits PokeAPI only for the specific IDs used in the grass/water pools, never at runtime. Effectively read-only after seeding.
- **Catches** (`user_id`, `species_id` → references the catalog, `caught_at`) — grows per user, stores nothing but the reference + a timestamp. A catch's display data (name/sprite) comes from joining against the catalog, not from duplicating it per row.

Ties into the still-deferred dummy-login system (see the earlier auth-design discussion this session) — catches are scoped per dummy user account, which is also what makes the per-user cap meaningful. Auth itself stays last in the build order, same as already decided.

## Character sprite & animation (implemented 2026-09-08)

`character.tsx` renders the character via the CSS sprite-sheet technique (fixed-size box, `background-image` + `background-size` + `background-position`), not `next/image` per-frame swapping — needed because these are animated multi-frame sheets, not standalone images.

- **Assets:** `_assets/character/char-still.png` (48×16px = 3 frames of 16×16 — down, up, left) and `char-motion.png` (96×16px = 6 frames of 16×16 — down×2, up×2, left×2, each pair a foot-alternation walk cycle). **There is no "right" art at all** — economy trick, mirrored from "left" via `transform: scaleX(-1)`.
- **`DIRECTION_SPRITES`** (in `character.tsx`) is the direction → frame-index lookup, built by slicing the sheets apart and inspecting each frame. The drawn pose faces **right** (not left, as an earlier pass of this doc incorrectly guessed from the sliced-frame images) — `left` is the one that mirrors it via `flip: true`. Current code (`left: {..., flip: true}`, `right: {...}` unflipped) is correct as-is — no bug here.
- **Display size — changed 2026-09-27:** now `CHARACTER_SIZE = spriteSize(32)` (5%, = 32px at the full 640px canvas), sized like every other sprite. It was originally a fixed 32px box on the reasoning that the character didn't need a collision-matched footprint — that expired once collisions were next (a px-sized character drifts out of scale with %-sized hitboxes on narrow screens). Consequence: the sprite-sheet math moved from px to %: `backgroundSize: ${frameCount * 100}% 100%` and `backgroundPosition: ${frameIndex / (frameCount - 1) * 100}% 0%` — note **no minus sign** and **`frameCount − 1`** (gaps between frames), since %-based `background-position` is an alignment point, not an offset. Height as `%` relies on `.canvas-main` being `aspect-square`. `image-rendering: pixelated` keeps the upscale crisp.
- **Debug guides (`guideClass`) use `outline`, not `border`** (changed 2026-09-27 in all 6 components): with `border-box`, a border shrinks the content area — on the character it made the repeating background bleed a sliver of the neighbor frame under the translucent border; on `<Image>` tiles it would shrink each tile 2px. Outlines don't affect layout. The zone-data-driven hitbox overlay (`debug-zones.tsx`, built 2026-09-30) is the tool for checking *collisions*; `guideClass` only shows where *images* are.
- **Walk-cycle timing:** `walkFrameCounter` (a `useRef`, pure tick-tally, no re-render needed) climbs every frame while moving; every `WALK_FRAME_INTERVAL` (currently `8`) ticks, it resets and flips `walkFrameIndex` (state, `0`/`1`) between the two frames in the current direction's `walk` pair. Resets to `0` the instant movement stops, so a later walk cycle always restarts clean rather than resuming mid-count.
- **Facing persistence:** `facingDirection` (state, defaults to `"down"`) only updates while a direction is actually active — never reset to "nothing" on release — so an idle character keeps facing whichever way it last walked, matching the genre convention, instead of reverting to some default look.

## Code organization & conventions (established 2026-09-27 → 2026-09-30)

File map (all under `app/apps/pokemon-playground/`):

| File | Job |
|---|---|
| `page.tsx` | Server component. Renders the canvas + all areas, `Character`, `DebugZones`. |
| `_components/area-*.tsx` (lake, tree-cluster, dirt, grass, house) | Each draws its tile grid (`*_PARTS` 2D array, `null` = empty cell) **and** exports its hitboxes as a named export `*_ZONE_BOXES = gridToRects(PARTS, startX, startY, tileSize)` below the grid. Default export = the component. |
| `_components/terrain-objects.tsx` | Shrubs (decorative, no collision) + sunflowers (collision TBD). |
| `_components/character.tsx` | `'use client'`. Position/facing/walk state, the `requestAnimationFrame` game loop (`tick`), sprite rendering. Owns `startMoving`/`stopMoving`; renders `<DPad>` and passes them down as props. |
| `_components/d-pad.tsx` | On-screen buttons (`BUTTONS: ButtonObject[]` of `{ direction, ariaLabel, Icon }` + one `.map()`, `<Icon />` renders a component stored in a variable) **and** the keyboard listeners (`KEY_DIRECTIONS`, `preventDefault()` only for our arrow keys so the page doesn't scroll). Props typed as `DPadProps` with `(direction: Direction) => void`. No `'use client'` needed — only imported by `Character`, already client. |
| `_components/debug-zones.tsx` | Hitbox overlay: maps `ALL_ZONES` → one translucent `<div>` per rect, colored by `debugColor` (inline `style`, not a dynamic Tailwind class), `z-5` (above areas `z-1`, below character `z-10`), `pointer-events-none`, `DEBUG_ON` flag → `return null`. Key = `${group.name}-${i}`. |
| `_lib/types.ts` | **Shared** types only: `Position`, `Rect`, `Direction`. |
| `_lib/constants.tsx` | `SIZE_CANVAS = 640`. (Should be renamed `.ts` — no JSX in it.) |
| `_lib/utils.ts` | Pure helpers: `spriteSize`, `clamp`, `clampToCanvas`, `rectsOverlap`, `gridToRects`. |
| `_lib/zones.ts` | **Single source of truth for areas**: `ZoneGroup` type + `ALL_ZONES` (`{ name, rects, debugColor, wander }` per area). Both the overlay and (soon) collision read from here. |

Conventions agreed:
- **Double quotes** (matches the rest of the repo + Next/shadcn/Prettier defaults). Backticks only for interpolation.
- **Imports:** relative (`../_lib/...`) inside this app — keeps it self-contained/portable; `@/` for site-wide shared code (`@/components/ui/button`). Rule of thumb: more than one `../` or leaving the feature folder → `@/`.
- **Exports:** components = default export; data/constants/helpers/types = named exports (even if only one), so names stay consistent across importers.
- **Types:** colocate until shared — a type used by one file stays in it (`SpriteFrames` in `character.tsx`, `DPadProps`/`ButtonObject` in `d-pad.tsx`); used by 2+ files → `types.ts`. `types.ts` holds only types, not values (`DIRECTION_DELTAS` is a value and stays in `character.tsx` — nothing else needs it). Don't move things for "might use later".
- **Avoid over-permissive types** (`Function`, `Record<string, X>` that overpromises) — they silently switch checking off. ESLint flags `Function` (`no-unsafe-function-type`).
- Components PascalCase (JSX requires a capital first letter to treat a tag as a component); object keys camelCase (`debugColor`, not `debug_color`).
- `cn()` for conditional classes; never interpolate dynamic Tailwind classes (`bg-${color}`) — use inline `style`.
- **After editing code inside a `useEffect`, do a full page reload** — Fast Refresh keeps already-attached listeners from the old effect (hit again 2026-09-30 with `preventDefault`).
- **Run ESLint, not just `tsc`** — they're separate tools; the editor only shows ESLint issues if the ESLint extension is installed. `npx eslint app/apps/pokemon-playground`.
